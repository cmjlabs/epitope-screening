# 论文讨论上下文：VZV gB/gE 表位预测、筛选与实验验证

更新时间：2026-11-24  
用途：跨电脑、跨会话与合作者/AI 继续讨论论文撰写。本文档汇总本轮对话中已经确定的事实、软件进展、历史数据背景、方法学草稿和仍需核对的问题。它不是最终论文，也不替代实际运行记录。

## 0. 给下一台电脑或下一位讨论者的简要说明

本项目研究水痘–带状疱疹病毒（VZV）Dumas 株包膜糖蛋白 gB 和 gE 的候选表位。蛋白登录号为 **P09257（gB）** 和 **P09259（gE）**。总体流程是：

`FASTA → IEDB MHC-I/MHC-II 预测 → 结合/排名/免疫原性筛选 → 20–30 aa 长窗口扫描 → MHC-I 与 MHC-II 人群覆盖率筛选 → 候选多肽 → 实验验证`

目前 GitHub 软件已整理为可下载的 Linux 网页版；Linux 可以在没有作者电脑、没有 Docker、没有系统 Python 的新环境中完成首次配置并运行本地 IEDB。Windows 版目前主要支持 IEDB 在线 API 或导入已有预测表，**Windows 本地 IEDB 暂不作为当前验证路径**。

论文现在应重点讨论两件事：

1. 如何准确描述“重新运行的新流程”，并与历史 IEDB 网页结果区分开；
2. 如何把计算筛选结果与后续实验验证逐一对应，而不把预测覆盖率写成实验保护率。

本轮重新运行的肽长要求是：**MHC-I 为 8–14 aa，MHC-II 为 11–30 aa**。注意：GitHub v0.4.0b1 软件默认的 MHC-II 是 15 aa，因此 11–30 aa 必须通过分析配置显式指定，不能在论文中写成软件默认值。

## 1. 项目背景与原始需求

最初需求是把已有网站中的表位筛选工具整理成可维护、可上传 GitHub、方便 Windows/Linux 用户运行的版本，并最终核对历史筛选结果能否复现。随后需求逐步明确为：

- 研究蛋白：P09257 和 P09259，即 VZV Dumas 株 gB、gE；
- 历史最终表：
  - `GB_VZVD_MHC_combined_20-30_filtered_0.8_with_properties_difficulty.xlsx`
  - `GE_VZVD_MHC_combined_20-30_filtered_0.8_with_properties_difficulty.xlsx`
- 历史表中的理化性质和 difficulty 字段暂不作为本次核对重点；首先核对肽序列、坐标和相应 HLA 覆盖率；
- 新流程需从 FASTA 开始，调用 IEDB 工具完成预测，再进行各层阈值筛选；
- 新用户从 GitHub 下载后应能操作，不应依赖作者电脑上开启网站；
- 不希望把 Docker Desktop 作为小白用户的第一步；
- 报告不能只保留最后一个表，必须包含原始预测、中间各阈值步骤和最终结果；
- 论文部分先撰写“预测—筛选—实验验证”中的计算方法部分，后续再补实验方法和结果。

## 2. 历史结果与新流程的关系

历史结果并不是完全由当前 GitHub 工具产生的。历史流程大致是：在 IEDB 网站上提交预测任务，再通过一系列脚本或表格进行阈值筛选。历史文件中可以看到：

- MHC-I 原始表类似 `IEDB_NETMHCⅠpan4.1_27allele_8-14length.csv`；
- MHC-II 原始表类似 `IEDB_NETMHCⅡpan4.3_27allele_11-30length.csv`；
- 历史 MHC-II 表含 11–30 aa 结果，并且使用了 EL 输出和 CD4Episcore 相关字段；
- 历史最终结果还包含 `results_all.xlsx`、理化性质和 difficulty 等后处理字段。

因此，不能直接把历史 Excel 表当成当前 v0.4.0b1 流程的正式复现结果。论文中建议区分：

- **历史分析**：用于说明过去如何得到候选肽；
- **新流程**：以当前 GitHub 版本、实际配置文件和运行记录为准；
- **复现比较**：只有在新流程实际对 P09257/P09259 运行完成，并明确模型模式、HLA 面板、阈值和覆盖率实现一致后才能下结论。

目前不能声称 P09257/P09259 已经完成严格等价性复现。已完成的是软件链路、Linux 本地 IEDB 和公开试跑数据的端到端验证。

## 4. IEDB 调用方案

### 4.1 在线 API

Windows 版可以通过 IEDB 官方在线接口提交任务。流程是按 HLA 批次提交、轮询任务状态、下载结果并合并。在线方式不要求本地安装 IEDB，但速度受网络和 IEDB 排队影响。

Windows 测试中曾出现以下错误：

```text
IEDB 拒绝任务：['The following are not valid alleles: DRB1*01:01, DRB1*03:01, DRB1*04:01, DRB1*04:05']
```

原因是 MHC-II 等位基因格式与 IEDB API 接受的格式不一致，代码随后增加了规范化映射。另一次错误是：

```text
ValueError: MHC-II 的 score 存在缺失或非数值；不会静默跳过筛选。
```

这是有意保留的严格校验：若输入结果缺少必需 score 或 score 不是数值，程序应报错，而不是静默删除记录。

### 4.2 Linux 本地 IEDB

Linux 版调用 IEDB Next-Generation T-cell 工具：

- TC1：`IEDB_NG_TC1-v0.2-beta.tar.gz`
- TC2：`IEDB_NG_TC2-v0.2.3-beta.tar.gz`
- 预测模型：NetMHCpan 4.1 和 NetMHCIIpan 4.3 的本地工具链；
- 软件会在首次配置时下载官方工具包、校验 SHA256、解压并配置独立运行环境；
- 官方工具包不直接打包进 GitHub 仓库，原因是体积、许可和分发责任；
- 用户不需要作者电脑保持开启，也不需要 Docker；
- 首次配置需要联网，正式预测完成后可在本地断网运行；
- Linux 网页版仅监听本机 `127.0.0.1`。

官方工具包大小约 2.4 GB，首次配置还会准备 Python 和依赖，耗时取决于网络和磁盘。完整使用步骤见 `docs/WEB_BEGINNER.md`。

### 4.3 为什么不把“单独 HTML”当作全部程序

HTML 页面可以作为操作界面和说明书，但不能独立执行本地 IEDB 模型。正确结构是：

`Start-Web → 本机后台服务 → 网页操作 → 本地 IEDB/筛选程序 → 下载结果`

因此新用户应下载完整 Release 压缩包，保留 `_internal` 等文件，并启动 `Start-Web`。只下载一个 HTML 文件不能完成本地预测。

- 首次配置能自动下载和配置官方 IEDB 工具；

## 7. 当前计算流程（论文应按此组织）

### 7.1 输入序列

从 UniProtKB 获取 VZV Dumas 株 gB 和 gE 的完整氨基酸序列，登录号分别为 P09257 和 P09259，保存为 FASTA。论文中还应补充实际下载日期、序列版本/校验值和完整序列长度。

### 7.2 HLA 面板

默认面板包含 27 个 MHC-I HLA 条目和 27 个 MHC-II 条目。MHC-II 中包含 DR 条目以及 DQ/DP α/β 链组合。正式论文应在补充材料中列出完整 HLA 面板和输入格式，不要只写“常见 HLA”。

### 7.3 IEDB 预测

使用本地 IEDB Next-Generation 工具，MHC-I 采用 NetMHCpan 4.1，MHC-II 采用 NetMHCIIpan 4.3。以 1 aa 为步长枚举：

- MHC-I：8–14 aa；
- MHC-II：11–30 aa。

对每条肽段和每个 HLA 保存 peptide、起止坐标、allele、IC50/BA 和 percentile rank 等原始字段。重复肽段位于不同坐标时保留其全部坐标。

### 7.4 阈值筛选

当前软件的筛选顺序为：

1. IC50/等位基因特异性 cutoff；
2. percentile rank；
3. score 下限；
4. score 上限；
5. 去重并保留位置、肽段和 HLA 关系。

当前配置草案如下，正式论文必须以实际运行的 settings JSON 和运行记录为准：

| 参数 | MHC-I | MHC-II |
|---|---:|---:|
| 肽长 | 8–14 aa | 11–30 aa |
| 预测模式 | NetMHCpan BA | NetMHCIIpan BA 4.3 |
| rank | ≤2% | ≤10% |
| IC50 | 等位基因特异性 cutoff；需核对 HLA-C | ≤1000 nM |
| score | 0–100 | −100–66 |
| 长窗口 | 20–30 aa | 20–30 aa |
| 人群 | World | World |
| 覆盖率条件 | ≥0.80 | ≥0.80 |

这里的 score 范围是当前项目配置，不应全部写成 IEDB 官方推荐阈值。score 也不能写成百分比概率。

### 7.5 长窗口与覆盖率

在每条蛋白序列上以 1 aa 步长遍历 20–30 aa 窗口。只有完整落在窗口内的已筛选短肽参与该窗口汇总。分别计算 MHC-I 和 MHC-II 人群覆盖率；窗口入选条件为：

```text
round(C_I, 4) >= 0.80 且 round(C_II, 4) >= 0.80
```

两类覆盖率分别达到 0.80，不等于联合人群覆盖率，也不等于实验保护率。程序中的 `combined_score = (C_I + C_II)/2` 仅为描述性平均值，当前不参与候选选择。

### 7.6 报告输出

每个任务应下载完整 ZIP，而不仅是最后一个 Excel 表。完整包应包括：

- 输入 FASTA 和输入表快照；
- IEDB 原始预测结果、请求记录、批次状态和日志；
- MHC-I/MHC-II 的 `step0_raw`、`step1_ic50`、`step2_rank`、`step3_score_min`、`step4_score_max`、`final`；
- 全部窗口、逐步覆盖率筛选结果和最终候选窗口；
- `filter_summary.csv`、`screening_settings.csv`、模型/软件版本和 SHA256 校验值；
- 失败或取消时已经生成的部分结果，并明确标记任务状态。

这样论文中可以报告每一层筛选保留了多少记录，审稿人也可以追溯从原始预测到最终候选的过程。

## 8. 可直接修改的论文“方法”草稿

下面这段可作为方法部分的起点，但方括号内容必须用实际运行记录补齐。

### 8.1 计算预测与表位筛选

从 UniProtKB 数据库获取水痘–带状疱疹病毒（varicella-zoster virus，VZV）Dumas 株包膜糖蛋白 gB 和 gE 的完整氨基酸序列，登录号分别为 P09257 和 P09259。两条序列以 FASTA 格式输入计算流程；序列版本、下载日期、长度和校验值列于补充材料。

采用 IEDB Next-Generation 本地工具进行 HLA 限制性肽段预测。MHC-I 和 MHC-II 结合预测分别使用 NetMHCpan 4.1 和 NetMHCIIpan 4.3 的 binding-affinity（BA）模式。以一个氨基酸为步长，枚举长度为 8–14 aa 的 MHC-I 肽段和 11–30 aa 的 MHC-II 肽段，并针对预先指定的 HLA 面板计算预测 IC50 和 percentile rank。预测结果保留肽段序列、来源坐标、HLA 分子及模型输出的原始字段。完整 HLA 面板见补充表 S[ ]。

预测记录依次按照结合亲和力、percentile rank 和免疫原性 score 进行筛选。MHC-I 使用预先指定的等位基因特异性 IC50 cutoff，并要求 percentile rank ≤2%；MHC-II 要求 IC50 ≤1000 nM 且 percentile rank ≤10%。免疫原性 score 的上下限分别按分析配置文件执行。所有边界条件均在程序中显式定义，缺失或非数值 score 不被静默跳过，而是使任务报错并保留错误日志。

### 8.2 候选长肽和人群覆盖率

为识别同时包含 MHC-I 和 MHC-II 候选表位的长肽区域，在 gB 和 gE 序列上以一个氨基酸为步长扫描 20–30 aa 窗口。仅将坐标完全包含于窗口内的已筛选短肽纳入窗口汇总。采用 IEDB Population Coverage 工具对应的 World 人群频率数据，分别估算每个窗口的 MHC-I 和 MHC-II 人群覆盖率。两类覆盖率均在保留四位小数后达到 0.80 的窗口定义为计算候选长肽。该指标表示基于 HLA 频率和预测表位的理论覆盖率，不代表个体免疫应答率或疫苗保护效力。

### 8.3 软件和可重复性

分析使用 Python 实现的 Epitope Screening v0.4.0b1 完成，代码托管于 GitHub（<https://github.com/cmjlabs/epitope-screening>），版本依据为提交 `38a2e17d064e01275aaf24a4eba23cc6a9e4f788`。IEDB 工具版本、操作系统、HLA 面板、肽长、阈值和输入序列均保存于每次任务的 settings、日志和结果包中。原始预测结果、每一步筛选结果、全部扫描窗口和最终候选表均予以保存，以便独立复核。

### 8.4 与实验验证的衔接

计算筛选得到的候选长肽按照序列、来源蛋白、起止位置、MHC-I/MHC-II 覆盖率和所包含的短表位逐一编号。后续实验使用相同编号的合成肽或相应抗原材料进行验证。实验方法中应明确肽段合成、纯度、样本来源、刺激条件、检测方法、阳性/阴性对照和判定标准；结果部分应逐一报告计算预测与实验信号之间的对应关系。预测覆盖率仅用于候选优先级排序，不应被表述为实验保护率。

## 9. 必须在论文定稿前核对的科学问题

### 9.1 免疫原性模型的验证长度

IEDB Class I Immunogenicity 的公开验证主要基于 9-mer；CD4Episcore 的公开验证主要针对 15-mer。结合预测肽长可以是 8–14 aa 和 11–30 aa，但这不代表免疫原性模型在所有这些长度上都具有相同验证程度。若本研究对全部长度直接使用 score，应在方法和讨论中明确这是探索性扩展，并避免写成“模型在所有长度均已验证”。

### 9.2 MHC-II DQ/DP 异二聚体

当前代码兼容旧流程，会对部分 DQ/DP α、β链进行拆分和映射。单条链的频率不必然等于完整异二聚体的频率。因此，在正式使用 0.80 覆盖率筛选并解释 DQ/DP 结果前，需要核对：

- 输入给 IEDB 的 DQ/DP 格式是否是完整 α/β 异二聚体；
- Population Coverage 频率表如何表示这些分子；
- 缺失链或缺失频率如何处理；
- 当前覆盖率是否应被称为“链级近似覆盖率”而不是完整异二聚体覆盖率。

这是当前最重要的方法学核查点之一。

### 9.3 MHC-I 专属 cutoff 与 HLA-C

默认面板中有 HLA-C*07:01 和 HLA-C*07:02，但内置专属 cutoff 表主要覆盖 HLA-A/B。若启用专属 cutoff，缺乏映射的记录可能被排除。论文必须报告：

- 预测面板有多少 HLA；
- 实际进入阈值筛选和覆盖率计算的 HLA 有多少；
- HLA-C 采用了什么 cutoff 或为何排除。

不能只写“预测了 27 个 MHC-I HLA”而不说明后续有效记录数。

### 9.4 BA、EL、rank 和 score 的区别

历史 CSV 中存在 EL 百分位、BA/IC50、CD4Episcore 和 immunogenicity combined score 等字段。新流程当前以 BA 模式为主。论文中必须逐一标明实际使用的字段，不能把 BA、EL、percentile rank 和免疫原性 score 合并称为“结合分数”。

### 9.5 历史结果与新结果是否混用

若新流程参数与历史流程不同，实验验证对象必须以实际新流程最终候选为准，或者在论文中明确这是“历史候选复核”而不是“新流程候选”。不要用新流程的方法描述历史 EL 结果，也不要用历史结果数字填充新流程的 Results。

## 10. 论文整体结构建议

### Methods

1. 病毒蛋白序列和版本；
2. HLA 面板及其来源；
3. IEDB/NetMHCpan/NetMHCIIpan 版本和预测模式；
4. MHC-I 8–14 aa、MHC-II 11–30 aa 的枚举方式；
5. IC50、rank、免疫原性 score 过滤顺序和阈值；
6. 20–30 aa 长窗口和坐标包含规则；
7. Population Coverage 的人群、频率数据和覆盖率判定；
8. 软件版本、配置文件、原始/中间/最终结果保存方式；
9. 实验验证方法及其与候选编号的对应关系。

### Results

建议按“输入—预测—逐层筛选—窗口—最终候选—实验验证”顺序写：

1. 两条蛋白长度和预测记录总数；
2. MHC-I、MHC-II 各阈值步骤的输入/保留数；
3. 20–30 aa 窗口总数和通过两类覆盖率条件的数量；
4. 最终候选序列、位置、HLA 数量和两类覆盖率；
5. 实验验证中每条肽的阳性/阴性信号及与预测的对应；
6. 历史结果复现时，单独报告一致和不一致的序列、位置、HLA 和覆盖率。

### Discussion

建议讨论：

- 同时结合 MHC-I 和 MHC-II 的长肽设计逻辑；
- 计算覆盖率对候选优先级排序的价值；
- 预测结果与实验结果不一致的可能原因（加工、呈递、免疫原性模型范围、样本 HLA、肽溶解性等）；
- HLA-DQ/DP 处理和 HLA-C cutoff 的限制；
- 历史 IEDB 网页流程与新本地流程的差异；
- 本地 IEDB、参数文件和完整结果包对可重复性的贡献；
- 后续需要实验证明，而不能由计算结果直接推出的结论。
